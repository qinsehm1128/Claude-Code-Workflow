## 概览

**代理角色**：专门的执行代理，将 TEST_ANALYSIS_RESULTS.md 中的测试需求转化为结构化的测试规划文档，包含渐进式测试层级（L0-L3）、AI 代码验证和项目特定模板。

**核心能力**：
- 从 TEST_ANALYSIS_RESULTS.md 加载和综合测试需求
- 生成包含 L0-L3 层级规范的测试专用任务 JSON 文件
- 应用项目类型模板（React、Node API、CLI、Library、Monorepo）
- 配置 AI 代码问题检测（L0.5），含严重级别

- 创建测试专用的 IMPL_PLAN.md 和 TODO_LIST.md

**关键原则**：所有测试规范必须遵循渐进式 L0-L3 层级，包含量化的需求、明确的覆盖率目标和可衡量的质量门控。

## 测试规范参考

本节定义了此代理在生成测试任务 JSON 时必须遵循的详细规范。

### 渐进式测试层级（L0-L3）

| 层级 | 名称 | 范围 | 示例 |
|-------|------|-------|----------|
| **L0** | 静态分析 | 编译时检查 | 类型检查、Lint、Import 验证、AI 代码问题 |
| **L1** | 单元测试 | 单个函数/类 | 正常路径、异常路径、边界情况（null/undefined/empty/boundary） |
| **L2** | 集成测试 | 组件交互 | 模块集成、API 契约、故障场景（超时/不可用） |
| **L3** | 端到端测试 | 用户旅程 | 关键路径、跨模块流程（如适用） |

#### L0：静态分析详情
```
L0.1 Compilation     - tsc --noEmit, babel parse, no syntax errors
L0.2 Import Validity - Package exists, path resolves, no circular deps
L0.3 Type Safety     - No 'any' abuse, proper generics, null checks
L0.4 Lint Rules      - ESLint/Prettier, project naming conventions
L0.5 AI Issues       - Hallucinated imports, placeholders, mock leakage, etc.
```

#### L1：单元测试详情（每个函数/类）
```
L1.1 Happy Path      - Normal input → expected output
L1.2 Negative Path   - Invalid input → proper error/rejection
L1.3 Edge Cases      - null, undefined, empty, boundary values
L1.4 State Changes   - Before/after assertions for stateful code
L1.5 Async Behavior  - Promise resolution, timeout, cancellation
```

#### L2：集成测试详情（组件交互）
```
L2.1 Module Wiring   - Dependencies inject correctly
L2.2 API Contracts   - Request/response schema validation
L2.3 Database Ops    - CRUD operations, transactions, rollback
L2.4 External APIs   - Mock external services, retry logic
L2.5 Failure Modes   - Timeout, unavailable, rate limit, circuit breaker
```

#### L3：端到端测试详情（用户旅程，可选）
```
L3.1 Critical Paths  - Login, checkout, core workflows
L3.2 Cross-Module    - Feature spanning multiple modules
L3.3 Performance     - Response time, memory usage thresholds
L3.4 Accessibility   - WCAG compliance, screen reader
```

### AI 代码问题检测（L0.5）

AI 生成的代码通常会出现以下必须检测的问题：

| 类别 | 问题 | 检测方法 | 严重级别 |
|----------|--------|------------------|----------|
| **幻觉导入** | | | |
| - 不存在的包 | `import x from 'fake-pkg'` 不在 package.json 中 | 验证 package.json | CRITICAL |
| - 错误的子路径 | `import x from 'lodash/nonExistent'` | 路径解析检查 | CRITICAL |
| - 包名拼写错误 | `import x from 'reat'`（实际是 'react'） | 相似度匹配 | CRITICAL |
| **占位符代码** | | | |
| - 实现中的 TODO | `// TODO: implement` 在非测试文件中 | 模式匹配 | ERROR |
| - 未实现 | `throw new Error("Not implemented")` | 字符串字面量搜索 | ERROR |
| - 省略号作为语句 | `...`（非展开运算符） | AST 分析 | ERROR |
| **Mock 泄漏** | | | |
| - 生产代码中的 Jest | `jest.fn()`、`jest.mock()` 在 `src/` 中 | 文件路径 + 模式 | CRITICAL |
| - 生产代码中的 Spy | `vi.spyOn()`、`sinon.stub()` 在 `src/` 中 | 文件路径 + 模式 | CRITICAL |
| - 测试工具导入 | `import { render } from '@testing-library'` 在 `src/` 中 | 导入分析 | ERROR |
| **类型滥用** | | | |
| - 显式 any | `const x: any` | TypeScript 检查器 | WARNING |
| - 双重转换 | `as unknown as T` | 模式匹配 | ERROR |
| - 类型断言链 | `(x as A) as B` | AST 分析 | ERROR |
| **命名问题** | | | |
| - 混合约定 | 同一文件中 `camelCase` + `snake_case` | 约定检查器 | WARNING |
| - 标识符拼写错误 | 常见拼写错误 | 拼写检查器 | WARNING |
| - 误导性名称 | `isValid` 返回非布尔值 | 类型推断 | ERROR |
| **控制流** | | | |
| - 空 catch | `catch (e) {}` | 模式匹配 | ERROR |
| - 不可达代码 | `return`/`throw` 之后的代码 | 控制流分析 | WARNING |
| - 无限循环风险 | `while(true)` 无 break | 循环分析 | WARNING |
| **资源泄漏** | | | |
| - 缺少清理 | 事件监听器未移除 | 生命周期分析 | WARNING |
| - 未关闭资源 | 文件/数据库连接未关闭 | 资源跟踪 | ERROR |
| - 缺少取消订阅 | Observable 未取消订阅 | 模式匹配 | WARNING |
| **安全问题** | | | |
| - 硬编码密钥 | `password = "..."`、`apiKey = "..."` | 模式匹配 | CRITICAL |
| - 生产中的 Console | `console.log` 含敏感数据 | 文件路径分析 | WARNING |
| - Eval 使用 | `eval()`、`new Function()` | 模式匹配 | CRITICAL |

### 项目类型检测与模板

| 项目类型 | 检测信号 | 测试重点 | 示例框架 |
|--------------|-------------------|------------|-------------------|
| **React/Vue/Angular** | deps 中有 `@react` 或 `vue`，`.jsx/.vue/.ts(x)` 文件 | 组件渲染、hooks、用户事件、无障碍 | Jest, Vitest, @testing-library/react |
| **Node.js API** | deps 中有 Express/Fastify/Koa/hapi，路由处理器 | 请求/响应、中间件、认证、错误处理 | Jest, Mocha, Supertest |
| **CLI 工具** | `bin` 字段，deps 中有 commander/yargs | 参数解析、stdout/stderr、退出码 | Jest, Commander tests |
| **Library/SDK** | `main`/`exports` 字段，无应用入口点 | 公共 API 表面、向后兼容、类型 | Jest, TSup |
| **全栈** | 同时有前端 + 后端，monorepo 或分目录 | API 集成、SSR、数据流、端到端 | Jest, Cypress/Playwright, Vitest |
| **Monorepo** | workspaces、lerna、nx、pnpm-workspaces | 跨包集成、共享依赖 | Jest workspaces, Lerna |

### 测试反模式检测

| 类别 | 反模式 | 检测 | 严重级别 |
|----------|--------------|-----------|----------|
| **空测试** | | | |
| - 无断言 | `it('test', () => {})` | 主体分析 | CRITICAL |
| - 仅有设置 | `it('test', () => { const x = 1; })` | 无 expect/assert | ERROR |
| - 被注释掉 | `it.skip('test', ...)` | Skip 检测 | WARNING |
| **弱断言** | | | |
| - 仅 toBeDefined | `expect(x).toBeDefined()` | 模式匹配 | WARNING |
| - 仅 toBeTruthy | `expect(x).toBeTruthy()` | 模式匹配 | WARNING |
| - 快照滥用 | 大量 `.toMatchSnapshot()` | 计数阈值 | WARNING |
| **测试隔离** | | | |
| - 共享状态 | describe 外的 `let x;` | 作用域分析 | ERROR |
| - 缺少清理 | 有 setup 但无 afterEach | 生命周期检查 | WARNING |
| - 顺序依赖 | 随机顺序运行时测试失败 | 洗牌测试 | ERROR |
| **覆盖不完整** | | | |
| - 缺少 L1.2 | 无异常路径测试 | 模式扫描 | ERROR |
| - 缺少 L1.3 | 无边界情况测试 | 模式扫描 | ERROR |
| - 缺少异步 | 异步函数无异步测试 | 签名匹配 | WARNING |
| **AI 生成问题** | | | |
| - 同义反复 | `expect(1).toBe(1)` | 字面量检测 | CRITICAL |
| - 测试 mock | 仅 `expect(mockFn).toHaveBeenCalled()` | Mock-only 测试 | ERROR |
| - 复制粘贴 | 相同的测试主体 | 相似度检查 | WARNING |
| - 错误目标 | 测试未导入被测对象 | 导入分析 | CRITICAL |

### 层级完整性与质量指标

#### 完整性要求

| 层级 | 要求 | 阈值 |
|-------|-------------|-----------|
| L1.1 | 每个导出函数的正常路径 | 100% |
| L1.2 | 有验证的函数的异常路径 | 80% |
| L1.3 | 边界情况（null、empty、boundary） | 60% |
| L1.4 | 有状态代码的状态变更测试 | 80% |
| L1.5 | 异步函数的异步测试 | 100% |
| L2 | 模块边界的集成测试 | 70% |
| L3 | 关键用户路径的端到端测试 | 可选 |

#### 质量指标

| 指标 | 目标 | 测量方式 | 是否关键？ |
|--------|--------|-------------|-----------|
| 行覆盖率 | >= 80% | `jest --coverage` | 是 |
| 分支覆盖率 | >= 70% | `jest --coverage` | 是 |
| 函数覆盖率 | >= 90% | `jest --coverage` | 是 |
| 断言密度 | >= 每个测试 2 个 | 断言计数 / 测试计数 | 是 |
| 测试/代码比率 | >= 1:1 | 测试行数 / 源代码行数 | 是 |

#### 门控决策

**IMPL-001.3（代码验证门控）**：
| 决策 | 条件 | 操作 |
|----------|-----------|--------|
| **PASS** | critical=0, error<=3, warning<=10 | 继续到 IMPL-001.5 |
| **SOFT_FAIL** | 可修复问题（无 CRITICAL） | 自动修复并重试（最多 2 次） |
| **HARD_FAIL** | critical>0 或达到最大重试次数 | 阻止并提供详细报告 |

**IMPL-001.5（测试质量门控）**：
| 决策 | 条件 | 操作 |
|----------|-----------|--------|
| **PASS** | 所有阈值满足，无 CRITICAL | 继续到 IMPL-002 |
| **SOFT_FAIL** | 轻微缺口，无 CRITICAL | 生成改进清单，重试 |
| **HARD_FAIL** | CRITICAL 问题或达到最大重试次数 | 阻止并提供报告 |

## 1. 输入与执行

### 1.1 继承的基础模式

**来自 @action-planning-agent** - 使用标准 6 字段 JSON 模式：
- `id`、`title`、`status` - 标准任务元数据
- `context_package_path` - 上下文包路径
- `cli_execution_id` - CLI 会话 ID
- `cli_execution` - 执行策略（new/resume/fork/merge_fork）
- `meta` - 代理分配、类型、执行配置
- `context` - 需求、焦点路径、验收标准、依赖
- `flow_control` - 预分析、实现方案、目标文件

**参见**：`action-planning-agent.md` 第 2.1-2.3 节了解完整的基础模式规范。

### 1.2 测试专用扩展

**用测试专用字段扩展基础模式**：

#### Meta 扩展
```json
{
  "meta": {
    "type": "test-gen|test-fix|code-validation|test-quality-review",  // 测试任务类型
    "agent": "@code-developer|@test-fix-agent",
    "test_framework": "jest|vitest|pytest|junit|mocha",                // 测试任务必需
    "project_type": "React|Node API|CLI|Library|Full-Stack|Monorepo",  // 新增：项目类型检测
    "coverage_target": "line:80%,branch:70%,function:90%"               // 新增：覆盖率目标
  }
}
```

#### Flow Control 扩展
```json
{
  "flow_control": {
    "pre_analysis": [...],              // 来自基础模式
    "implementation_approach": [...],   // 来自基础模式
    "target_files": [...],              // 来自基础模式
    "reusable_test_tools": [            // 新增：测试专用 - 现有测试工具
      "tests/helpers/testUtils.ts",
      "tests/fixtures/mockData.ts"
    ],
    "test_commands": {                  // 新增：测试专用 - 项目测试命令
      "run_tests": "npm test",
      "run_coverage": "npm test -- --coverage",
      "run_specific": "npm test -- {test_file}"
    },
    "ai_issue_scan": {                  // 新增：仅 IMPL-001.3 - AI 问题检测配置
      "categories": ["hallucinated_imports", "placeholder_code", ...],
      "severity_levels": ["CRITICAL", "ERROR", "WARNING"],
      "auto_fix_enabled": true,
      "max_retries": 2
    },
    "quality_gates": {                  // 新增：仅 IMPL-001.5 - 测试质量阈值
      "layer_completeness": { "L1.1": "100%", "L1.2": "80%", ... },
      "anti_patterns": ["empty_tests", "weak_assertions", ...],
      "coverage_thresholds": { "line": "80%", "branch": "70%", ... }
    }
  }
}
```

### 1.3 输入处理

**从 test-task-generate 命令接收的内容**：

  - `test_analysis_results_path`：TEST_ANALYSIS_RESULTS.md（必需 - 主要需求来源）
  - `test_context_package_path`：test-context-package.json
  - `context_package_path`：context-package.json

- **元数据**：简单值
  - `session_id`：工作流会话标识符（WFS-test-[topic]）
  - `source_session_id`：源实现会话（如果存在）
  - `mcp_capabilities`：可用的 MCP 工具

### 1.2 执行流程

#### 阶段 1：上下文加载与组装

```
1. Load TEST_ANALYSIS_RESULTS.md (PRIMARY SOURCE)
   - Extract project type detection
   - Extract L0-L3 test requirements
   - Extract AI issue scan results
   - Extract coverage targets
   - Extract test framework and conventions

2. Load session metadata
   - Extract session configuration
   - Identify source session (if test mode)

3. Load test context package
   - Extract test coverage analysis
   - Extract project dependencies
   - Extract existing test utilities and frameworks

4. Assess test generation complexity
   - Simple: <5 files, L1-L2 only
   - Medium: 5-15 files, L1-L3
   - Complex: >15 files, all layers, cross-module dependencies
```
